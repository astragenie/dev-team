# Architect review SLICE-77 (FEAT-165 SLICE-A: cost-report -> OTel span backfill)

## Verdict

NEEDS_FIX: two AC-1 line-cap violations and one schema-fidelity bug in cache_creation_tokens. All three are mechanical fixes; no architectural rework required. The trace shape, determinism, schema design, and idempotency are sound and ready for SLICE-B to build against.

Confidence: 0.78 - high on architecture/contract review (Zod shape, deterministic id scheme, parent-child links verified against the committed JSONL fixture); lower because test execution is deferred to crew:verifier per scope.

## Strengths

1. Span schema is OTLP-correct and forward-compatible. The attributes field is z.record(SpanAttrValueSchema) - an open map - so SLICE-C can additively inject prompt_id and prompt_version with zero schema churn. SpanKindSchema, SpanStatusSchema, and timeUnixNano as decimal string all match the OTLP/JSON contract Langfuse ingests at /api/public/otel/v1/traces. No z.any() or z.unknown() escape hatches - strict boundary validation per the scripts/lib/schemas.ts precedent.

2. Deterministic id scheme is robust and stable. newTraceId(runId) plus newSpanId(runId + .root | .phase.build | .agent. + model) derives all ids from the immutable filename timestamp plus structural literals, so two backfill runs on the same cost report produce byte-identical JSONL. The seed scheme does NOT include the parsed usd, totalTokens, or window-time fields, so minor whitespace drift in the source cost report will not shift trace/span ids - only a new runId or a new model in modelMix will. Correct discrimination.

3. Pure-function decomposition holds the boundary. costReportToSpans is I/O-free, has no Date.now() or Math.random(), and parses every emitted span through SpanRecordSchema.parse(...) before returning - schema doubles as contract and runtime guard. The CLI layer cleanly owns I/O, glob filtering, exit-code policy, and the optional --emit-observability stderr line, with process.exitCode = N then return per repo HARD RULES (no process.exit() in any of the five new files - verified by grep).

4. Aggregate-cost-report skip prevents double-counting. loadCostReport throws a typed AggregateReportSkipped on aggregate_all true, loadCostReportSafe converts that to null, the CLI silently skips. AC-6 is covered both at the loader unit-test layer and the CLI integration-test layer. The committed 20260607T122544Z.jsonl fixture (3 spans, single trace, parent links chain correctly) demonstrates the end-to-end shape SLICE-B can build against.

5. Reuse over duplication. Loader imports parseFrontmatterBlock, parseModelMix, parseHeaderFields, parseTokenFields, and parseDiagnosticFields from scripts/lib/briefing/collect-cost-parser.ts - no regex duplication. Only parseToolUsageMap and parseCacheCreate1h are net-new, both under 10 lines.

### 3. cache_creation_tokens drops cache_create_5m: silent under-reporting

- File: scripts/lib/telemetry/cost-report-to-spans.ts line 87, paired with scripts/lib/telemetry/cost-report-loader.ts line 128.
- Code: const cacheCreationTokens = report.cacheCreate1h;
- Spec mandate (SLICE-77 line 79): usage.cache_creation_tokens equals cache_create_1h plus cache_create_5m; backfill collapses 5m plus 1h since OTel attr does not distinguish.
- Consequence: For the committed FEAT113 fixture cache_create_5m is 0, so the bug is silent today. For any slice with non-zero 5m (common on shorter / interactive slices), usage.cache_creation_tokens under-reports. SLICE-B and Langfuse cost dashboards will show wrong cache-creation totals on backfilled traces.
- Fix: loader exposes a cacheCreate5m field alongside cacheCreate1h (the underlying parser at collect-cost-parser.ts line 182 already sums both into cacheWriteTokens - reuse that, or parse 5m separately at loader lines 79-81). Builder sums both at line 87. Add a unit test against a synthetic CostReport with cacheCreate5m of 1000 and cacheCreate1h of 2000 asserting the agent span usage.cache_creation_tokens is 3000 to prevent silent regression.

## Non-blocking findings (advisory)

### N-1. cost.usd per agent span uses model-mix entry.usd - correct for now

For a single-model cost report (the FEAT113 fixture), entry.usd equals report.usd. For multi-model reports, entry.usd is each model share. Math holds, but add a one-line comment at builder line 105 documenting that cost.usd is per-model not per-run, so SLICE-B does not accidentally double-count by emitting a roll-up cost.usd on the root span.

### N-2. derivedFeatureId short-circuits on frontmatter even when stale

Loader line 158: if (report.featureId) return report.featureId. If a cost report frontmatter feature value FEAT-099 disagrees with the run-title FEAT-113 SLICE-37 (mis-attributed during loop run), frontmatter wins. Probably correct (frontmatter is more authoritative), but a comment would prevent SLICE-B reviewers from flagging it as a bug.

### N-3. --only glob filter is positional-only

CLI lines 77-83 convert the star glob to .* and anchor with caret and dollar. Works for the spec star-feat113-star case, but does NOT support question-mark (single-char) or [abc] (charclass) despite the spec calling it fnmatch-style. Either tighten the spec wording to glob-with-only-star or expand the converter. Non-blocking - no test exercises the other fnmatch features.

### N-4. parseFrontmatterBlock regex does not tolerate Windows line endings between --- delimiters

collect-cost-parser.ts line 34 uses a strict LF newline. The body line split (line 37) tolerates CRLF. If a cost report is ever written with CRLF (Git autocrlf on a Windows worktree commit), frontmatter parsing silently returns an empty object. Inherited from upstream, not a SLICE-77 regression - but worth noting since this worktree is on Windows.

## Open questions for SLICE-B / SLICE-C author

1. Should the root span carry rolled-up cost? Currently slice.run has no cost.usd attribute, only per-model agent spans do. Langfuse roll-up math will sum the children (correct), but Tempo/Jaeger users wanting a single number on the root have to aggregate. Decision deferred to SLICE-B (live exporter) where the choice is more visible.

2. branch unknown literal vs omitting the attribute. Reviewer lens 4 asked this. Decision in builder line 44 is to emit unknown so consumers can distinguish backfill, data unrecoverable from live bridge missing data bug. Same for agent unknown (line 99). Defensible, but only if SLICE-B documents the semantic: unknown equals backfill, missing-attr equals live-bridge bug. Without that documentation pair, the literal can read as a default-fallback and SLICE-B might propagate it. Suggest: add a doc paragraph in docs/observability/langfuse-bridge.md (introduced by SLICE-B) calling out the literal as a backfill marker.

3. Should the schema pre-allocate prompt_id and prompt_version as optional attrs now? Currently they are not reserved keys - they are future entries in the open attributes map. Forward-compatible (zero schema churn for SLICE-C), but consumers may want strong typing on those two. Light-touch suggestion: SLICE-C introduces a PromptAttrsSchema that extends SpanAttrValueSchema records without touching the core. The current shape does not block that.

## Schema and boundary risks for SLICE-B integration

- R-1 (low). events: z.array(SpanEventSchema).default([]) is fine for backfill (empty array) and for live (populated). SLICE-B can emit handoff_written, tool_call, bash_gate events without schema change.
- R-2 (medium). SLICE-B BatchSpanProcessor will emit spans as @opentelemetry/sdk-node Span objects, not the plain SpanRecord shape. The SDK OTLP/JSON exporter uses traceState, links, droppedAttributesCount, etc. - extra fields the current schema rejects under default strict mode. Either (a) extend the schema with .passthrough() or .catchall() for forward fields, or (b) document that the backfill SpanRecord is a strict subset of the SDK span shape and SLICE-B uses a different (OtlpSpanSchema) for SDK-side validation. Recommend (a): add .passthrough() to SpanRecordSchema so SLICE-B can validate live spans through the same schema without breaking SLICE-A invariants.
- R-3 (low). cache_creation_tokens fidelity bug (Critical 3) - once fixed, SLICE-B may emit two attrs (usage.cache_creation_5m_tokens plus usage.cache_creation_1h_tokens) per the spec note line 206, AND keep the collapsed usage.cache_creation_tokens for Langfuse-native dashboards.
