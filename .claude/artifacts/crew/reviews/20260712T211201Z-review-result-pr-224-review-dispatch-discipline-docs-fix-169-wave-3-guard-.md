- Risks: 1. [BLOCKING] `commands/parallel.md:37-42` — technical inaccuracy in the prescribed mechanism. The added text says each parallel `Agent` call "MUST also set `isolation: \"worktree\"` pointed at ... the worktree path the prior `dispatch prepare` step just returned." Per the `Agent` tool's own schema, `isolation` is a bare string enum (`"worktree" | "remote"`) with no path/target argument, and its `"worktree"` mode *always creates a brand-new temporary worktree* — it cannot be pointed at or attached to a path created by an external step. `commands/parallel.md`'s workflow (step 7) already creates the N worktrees via the external `loop dispatch prepare` CLI *before* the Agent calls. If a dispatcher follows this doc literally and sets `isolation: "worktree"` on those calls, the harness will mint a *second, unrelated* temp worktree per call — the subagent ends up working in neither the CLI-prepared tree nor anywhere `dispatch finalize` (step 7's last bullet) knows to merge from. That silently defeats the parallel-merge flow rather than fixing #169's cwd-pinning gap. The only mechanism that actually attaches a dispatched subagent to a *pre-existing* path is `EnterWorktree({path: ...})`, called by the subagent itself as its first action from its launch directory (confirmed via the `EnterWorktree` tool description: "on first entry from the launch directory, the path must appear in `git worktree list` ... paths registered by neither are rejected" — no `isolation:` prerequisite, no `.claude/worktrees/` restriction for that first-entry case). The fix should instruct the dispatch prompt embedded in each `Agent` call to make the subagent's first action `EnterWorktree({path: "<worktree path dispatch prepare returned>"})`, and should NOT recommend `isolation: "worktree"` for this specific call site (that flag is for when the harness itself should create the worktree, which conflicts with `dispatch prepare` already having done so). This same "isolation: worktree (or EnterWorktree path: form)" phrasing is inherited verbatim from the already-signed-off design doc (`docs/design/2026-07-10-subagent-lifecycle-reliability.md:159-161`, `.claude/artifacts/crew/designs/2026-07-12-subagent-lifecycle-guards.md:181-182/187`), so this is a pre-existing inaccuracy the PR propagates into the live command file rather than one it introduces fresh — but `commands/parallel.md` is the file with the literal #169 repro, so getting the mechanism wrong here is the one place it actually matters at dispatch time.
