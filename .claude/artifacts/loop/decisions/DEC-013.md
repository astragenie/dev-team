# DEC-013: Gate contract drift-check on `errors.length === 0`

## Context

Comparing committed TS against regenerated TS is only meaningful for an otherwise-valid spec. When redocly lint fails (or the spec is not OpenAPI 3.1, or TS generation throws), the regenerated output is garbage and the drift comparison is noise. Gating the drift block on `errors.length === 0` makes drift a *second-stage* check that only runs once the spec is structurally sound.


## Decision

We will run the committed-vs-regenerated TS drift check only when the spec is
otherwise valid — i.e. gate the drift block on `errors.length === 0` (no redocly
lint failure, OpenAPI-3.1 marker present, TS generation succeeded). Drift becomes
a second-stage check that runs after structural validation passes.

## Consequences

### Positive

- Negative fixtures fail for their intended reason (lint) only — no conflated `drift: committed TS missing`.
- Valid specs are unaffected: real drift is still caught (verified — the existing drift test uses `runLint:false` with a drifted TS, so `errors` is empty at the gate and drift runs).

### Negative

- A spec that lints clean but fails the 3.1-marker check will now also skip drift — drift is no longer reported independently of other validity errors. Acceptable: an invalid spec shouldn't be drift-compared anyway.

### Neutral

- Drift is now ordered after lint/3.1/generation in the failure-reporting hierarchy; tooling that scraped for "drift" on broken specs will no longer see it.

## Alternatives considered

- **Isolate the negative fixture in the CI wrapper** (skip the drift step for that one file) — rejected: pushes the concern into CI YAML instead of fixing the tool, and any future negative fixture would re-trip the same conflation.
- **Drop the committed-TS-missing branch entirely** — rejected: valid specs legitimately need the "you forgot to commit the regenerated TS" signal.
