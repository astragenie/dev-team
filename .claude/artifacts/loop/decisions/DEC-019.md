# DEC-019: Drop SLICE-A1 (--update CLI semantics)

## Context

`tests/artifact-stub-and-update.test.ts` scenarios 3, 4, 5 (lines 88-253) already exercise `--update` for write-handoff/review-result/validation-result. Scenarios 7-9 cover `--scaffold` and scaffold-then-update flow. Prong B prerequisite met without any CLI work.


## Decision

We will drop SLICE-A1 (the planned CLI scope for adding `--update` / `--scaffold` idempotency). The `crew write-handoff`, `crew write-review-result`, `crew write-validation-result`, and `crew write-deployment-check` CLI commands already support double-call with `--update <path>` and pre-existing-stub creation via `--scaffold`. SLICE-A1 (originally planned to add this support) is **DROPPED** — the support already shipped in SLICE-70's harness work.

FEAT-161 Prong B (SLICE-72) and any future stub-on-entry slices can proceed directly to prompt edits with no CLI scope needed.

## Consequences

### Positive

- FEAT-161 Prong B (SLICE-72) can proceed directly to prompt edits; zero CLI scope needed.
- Zero risk of CLI regression on the existing idempotency contract — the shipping test suite already covers it.
- Future slices (stub-on-entry pattern) inherit the contract without needing a separate CLI story.

### Negative

- None surfaced.

### Neutral

- SLICE-A1 ticket is formally closed as unnecessary; no follow-up work required.

## Evidence

`tests/artifact-stub-and-update.test.ts` exercises the idempotency contract:

- **Scenarios 3, 4, 5** (lines 88–253): `--update` for `write-handoff`, `write-review-result`, and `write-validation-result` respectively — each verifies that a second call with `--update <path>` overwrites the stub at the same path with the real verdict.
- **Scenarios 7, 8, 9**: `--scaffold` flag for the three write-* commands and the scaffold-then-update flow end-to-end.

All scenarios green as of SLICE-70 (2026-06-13).

## Alternatives considered

- **Option A: Ship SLICE-A1 as planned** — add `--scaffold` / `--update` support via a CLI code change. Rejected because the support already exists; shipping it again would be duplicate work and introduce regression risk on a working contract.
