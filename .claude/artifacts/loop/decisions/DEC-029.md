# DEC-029: Deprecation plan for the escalated_to_lead workflow-badge alias

## Context

FEAT-180 (v2.0.0) renamed the workflow-escalation concept from `lead` to
`dispatcher` and introduced `escalated_to_dispatcher` as the canonical
`mark-badge` value, keeping `escalated_to_lead` as a backward-compat alias
in `scripts/lib/workflow-state.ts`'s `BADGE_HANDLERS` map (lines 290-301).
Both names resolve to the identical gate write —
`[run.gates, "escalation"] → status: "escalated"` — so the alias has never
been a second concept, only a second accepted spelling of the same CLI
input.

PR #243 ("Slice B", merged as `8f0b88e4`) closed the *other* half of the
incomplete v0.41 rename — the `"lead"`/`"lead-session"` wire-value
*defaults* in `scripts/crew.ts` (handoff `to:`, claim/approval owner
defaults) — but explicitly deferred the `escalated_to_lead` **badge name**
alias, since it is a distinct surface (a CLI-accepted enum value with its
own regression tests and a cross-plugin documentation dependency in
runner-plugin) that deserves its own reviewed deprecation plan rather than
folding into a mechanical wire-defaults slice. This DEC is that plan.

**Scope correction on the halt-badges.md coupling.** The originating
inventory framed runner-plugin's `docs/halt-badges.md` as a surface this
alias is documented in. That is not accurate as of 2026-07-16: the two
registries are structurally distinct (crew's `mark-badge`/`gates.*`
workflow badges vs. loop's own `snapshot.*` walker halt-signals), and
`escalated_to_lead`/`escalated_to_dispatcher` has never been a
`snapshot.*` field. Bridging the two registries so a crew `escalation`
gate can trip a loop `snapshot.*` halt-badge would be a legitimate, but
separate and much larger, FEAT — not part of this deprecation. If the
operator wants that bridge, file it as its own FEAT; do not conflate it
with removing this alias.

## Decision

We will treat this as **emit-new / accept-both-on-read, time-boxed**,
which is what the codebase already effectively does — not a new
"dual-emit" mode. No live code path emits `escalated_to_lead` today; only
the `mark-badge` CLI still *accepts* it as external input. The plan
narrows to: mark the alias formally deprecated, hold a fixed window, then
delete CLI acceptance + the two pinning tests + the stale-drift doc
mentions in one slice.

**Why not dual-emit:** there is nothing to dual-emit — FEAT-180 already
completed that half of the migration (every live emit site uses
`escalated_to_dispatcher`). Reintroducing dual-emit would be strictly
backward motion.

**Why not "leave the alias forever":** an unbounded backward-compat alias
with no removal criterion is exactly the kind of drift `NO_LEAD_REF_REQUIRED`
(v0.41) and the Slice B regression guard
(`tests/no-legacy-lead-wire-defaults.test.ts`) were built to prevent
elsewhere in this repo; leaving one CLI-enum value permanently exempt is
inconsistent with that established convention.

### Phase 1 — mark deprecated (this DEC's implementation slice, dev-team)

1. Add a lightweight `deprecated?: boolean` note to the
   `escalated_to_lead` entry's surrounding comment in
   `scripts/lib/workflow-state.ts` (no `BadgeDefinition`/`badge-catalog.ts`
   refactor exists yet — FEAT-181's "Acceptance hints" catalog-file design
   was not built that way; `docs/standards/badge-catalog.md` is currently
   hand/generated from the flat `BADGE_HANDLERS` map directly, so the
   deprecation marker lives as a comment + a one-line stderr warning in the
   `mark-badge` CLI handler when `--badge escalated_to_lead` is passed, not
   as a typed catalog field).
2. Fix the stale-drift doc mentions so `escalated_to_lead` is never
   presented as co-equal/primary: `CLAUDE.md:243`,
   `docs/architecture/architecture.md:138,156`.
3. `docs/standards/badge-catalog.md:34` — add the target removal release
   to the existing "backward-compat alias" row.
4. No behavior change: the CLI still accepts and resolves the alias
   exactly as before, now with a visible warning.

### Phase 2 — deprecation window

- **Window:** minimum of 2 minor dev-team releases *or* 45 days,
  whichever is later, measured from the release that ships Phase 1
  (current version at DEC time: dev-team v0.66.0).
- **Kill criteria** (both must hold before Phase 3 proceeds):
  1. Zero live (non-archival) invocations of `--badge escalated_to_lead`
     found by repo grep across dev-team AND runner-plugin, excluding
     `.claude/artifacts/**`, `docs/superpowers/**` archives, and the
     intentional regression-test/allowlist files themselves.
  2. The window has elapsed per above.

  No `MIN_CREW_VERSION` precondition gates Phase 3 — there is nothing
  for a pre-Phase-3 version floor to protect, since runner-plugin has
  zero code readers of this field (see inventory above; independently
  re-verified against the whole `src/` tree, not just the two files
  originally cited) and the field is never persisted by name (`applyBadge`
  in `scripts/lib/workflow-state.ts` writes only the resolved
  `{status, updatedAt, note}` to `gates.escalation`, never the literal
  badge-name string, so there is no artifact for read-side tolerance to
  need to outlive). The only `MIN_CREW_VERSION` bump this plan calls for
  is the one in Migration order step 4 / Version gate below, which is a
  **Phase 3 output** (a follow-up runner-plugin PR filed after removal
  ships), not a Phase 2 input precondition — an earlier draft of this DEC
  stated a third kill criterion requiring that bump before Phase 3, which
  contradicted the Migration Order/Version Gate sections below and was an
  unsatisfiable condition (nothing in the plan bumps `MIN_CREW_VERSION`
  before Phase 3 exists to bump it to). Dropped in review
  (2026-07-16) rather than reworded, since the zero-dependency finding
  means no version gate is actually needed here.

### Phase 3 — removal (future slice, dev-team; coordinate release notes with runner-plugin)

1. Delete the `escalated_to_lead` entry from `BADGE_HANDLERS`
   (`scripts/lib/workflow-state.ts:297-301`).
2. Remove `escalated_to_lead` from the `mark-badge` CLI accept list and
   help text (`scripts/crew.ts:418`); a caller passing it now gets the
   same "unknown badge" error as any other invalid value.
3. Delete or repoint the two pinning tests
   (`tests/cli-workflow.test.ts:574-593`,
   `tests/cli-synthesis-cost.test.ts:176-211`) to assert against the
   canonical name only.
4. Drop the alias row from `docs/standards/badge-catalog.md`.
5. **Same slice, runner-plugin:** drop the `(alias escalated_to_lead)`
   parenthetical from `skills/loop-discipline/SKILL.md:43`. This is a
   one-line prose edit with no code dependency, but it must not land
   *before* Phase 3 ships in dev-team (see Migration order) or it would
   describe behavior that is still true for any pinned older crew.

## Migration order

**dev-team ships first, in every phase.** dev-team owns the field; there
is no runner-plugin code that reads it, only one documentation sentence
describing dev-team's current behavior to an LLM agent. Concretely:

1. dev-team Phase 1 lands (deprecation warning + doc fixes) — no
   runner-plugin action required, the alias still works exactly as
   documented today.
2. Window elapses.
3. dev-team Phase 3 lands (removal) and bumps its own release version.
4. runner-plugin, in a follow-up PR, bumps `MIN_CREW_VERSION` to that
   release and edits the one SKILL.md line in the same PR. This can land
   any time after dev-team Phase 3 ships — there is no reason for
   runner-plugin to move first, and moving first would make the SKILL.md
   text inaccurate for any consumer still on a pre-removal crew (a
   `MIN_CREW_VERSION` floor does not stop a consumer from being on an
   *older* satisfying version between the floor and the removal release
   unless the floor is raised to meet it).

## Version gate

`src/scripts/lib/plugin-identity.mts::MIN_CREW_VERSION` in runner-plugin
currently pins `0.57.0` (dev-team is at `0.66.0` as of this DEC). Bumping
`MIN_CREW_VERSION` to the Phase 3 removal release is the mechanism that
lets runner-plugin's `/runner:install` refuse to configure a repo against
a crew version old enough to still rely on the alias's documented
behavior, keeping the loop-discipline prose truthful for every install
that passes the gate. This bump belongs to the runner-plugin PR in
Migration order step 4, not to the dev-team removal PR.

## Rollback story

- **Phase 1 rollback:** revert the single warning/doc-fix commit; the CLI
  behavior was unchanged by Phase 1, so this is a no-risk revert.
- **Phase 3 rollback:** revert the removal commit. Because `gates.escalation`
  state is identical regardless of which name wrote it, no data migration
  or backfill is needed in either direction — reverting restores CLI
  acceptance of the legacy name and the two pinning tests, and any
  `workflow-state.json` written in the interim (necessarily via the
  canonical name only, since the alias would have been rejected) remains
  valid and unaffected.
- **runner-plugin rollback:** revert the `MIN_CREW_VERSION` bump and the
  SKILL.md line together; no data surface involved.

## Halt-badge registry update requirement

Per runner-plugin's `CLAUDE.md` read-first item 6
(`docs/halt-badges.md`), any slice that introduces a **new**
`snapshot.*` halt-badge field must update that registry in the same
slice. This deprecation does not add, remove, or rename any `snapshot.*`
field, so `docs/halt-badges.md` is **not touched by Phase 1 or Phase 3**
of this plan — see "Scope correction" in Context above. This DEC
explicitly does not authorize editing that file; a future FEAT bridging
the crew `escalation` gate into loop's halt-badge schema would need to
satisfy that checklist itself, on its own merits.

## Consequences

### Positive

- Closes the one deferred surface from Slice B (#243) without inventing a
  new naming decision — the canonical name is already load-bearing
  everywhere except CLI input acceptance.
- Kill criteria are objectively checkable (grep + version + elapsed time),
  not a judgment call, matching the bounded reject/retry pattern this repo
  already uses elsewhere (see DEC-075 in runner-plugin for the analogous
  architect-gate pattern).
- No data-format risk: the gate value written is identical regardless of
  input spelling, so there is nothing to backfill or dual-write during the
  window.

### Negative

- Anyone with a hand-rolled script or muscle-memory still typing
  `--badge escalated_to_lead` after Phase 3 gets a hard CLI error instead
  of a warning; mitigated by the Phase 1 stderr warning giving advance
  notice for at least one full window.
- `MIN_CREW_VERSION` bumps are a blunt instrument — they gate the entire
  install, not just this one alias — so runner-plugin should batch this
  bump with any other pending version-floor reasons rather than issuing a
  bump for this alone if one is already queued.

### Neutral

- The `docs/standards/badge-catalog.md` / `BADGE_HANDLERS` architecture
  stays a hand-maintained flat map through this deprecation; FEAT-181's
  originally scoped `badge-catalog.ts` + `BadgeDefinition.deprecated`
  typed refactor was not built and is not a prerequisite for this plan —
  it would make Phase 1's marker cleaner but is independently valuable
  work, not blocking.

## Alternatives considered

- **Dual-emit (write both names to the artifact / event stream).**
  Rejected — there is no consumer that reads the badge *name* rather than
  the resolved `gates.escalation.status`; dual-emitting would only
  duplicate data with no reader benefit, and would reintroduce the
  `escalated_to_lead` string into live emit paths that FEAT-180 already
  removed it from.
- **Immediate removal, no deprecation window.** Rejected — even though no
  live prompt or script emits the alias, an operator's ad-hoc shell alias,
  saved snippet, or muscle memory could still type it; a silent hard
  break with no warning period is unnecessary risk for a change with a
  cheap warning-first alternative.
- **Leave the alias permanently.** Rejected — inconsistent with this
  repo's own drift-prevention convention (`NO_LEAD_REF_REQUIRED`,
  `tests/no-legacy-lead-wire-defaults.test.ts`) and leaves a
  documentation footnote in a second plugin (runner-plugin) load-bearing
  indefinitely for a decision this repo already made.
