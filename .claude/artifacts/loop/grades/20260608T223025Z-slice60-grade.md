## Lessons

- The `repo` field appearing twice (once in the mapped type, once in the manual intersection) is a latent `never` trap: if `--repo` ever gains `boolean: true` in FLAG_SPEC, `string & boolean = never` silently breaks flag access. Reviewer caught it; builder should have noticed during the intersection design.
- Pure TypeScript type-level refactors can have subtle runtime-shape implications that require tracing each special-cased field manually.
- 5 file re-reads in the cost report suggests the builder lost track of which FLAG_SPEC entries were handled. Maintaining a checklist of aliased/special-cased keys before editing would prevent this.

## Followups

- Harden `FlagKey` mapped type: `Exclude<FlagKey, 'repo'>` in the mapped arm, keep only the manual `& { repo: string }` intersection. Eliminates the latent never trap. (Reviewer required follow-up — marked as optional.)
- Consider adding a compile-time test that asserts `Flags['repo']` is `string` after any future FLAG_SPEC change.

## What went well

Clean elimination of drift-prone duplication: single `FLAG_SPEC` array now owns flag names, booleans, and aliases. TypeScript enforces sync at compile time. All 470 tests pass. `FLAG_SPEC.length` count test added per AC.

## What went wrong

Latent `never` trap in the `repo` field intersection. Could have been caught by tracing all special-cased fields during design.

## What I would do differently next time

Before writing the mapped type: list all fields that appear in FLAG_SPEC with non-standard handling (`boolean`, aliased keys, `repo`), and decide upfront which arm each belongs to. Prevents the intersection ambiguity.
