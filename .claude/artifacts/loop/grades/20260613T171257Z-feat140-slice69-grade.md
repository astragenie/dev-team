## Lessons

- Stale IDE diagnostic pattern confirmed twice in one slice — once after initial build, once after fix bundle. `bun run typecheck` exit 0 trumps inline `<new-diagnostics>` snapshot every time. The diagnostic feed lags real compiler state.
- Plugin observability ceiling needed enforcement mid-spec — spec-writer's first pass shipped JSON+ULID+ISO timestamps because the FEAT triage_notes mentioned "observability of security checks". The fix was a project-memory rule that distinguishes plugin AC from service AC. Cost of catching late: one full Edit cycle.
- Executable canonical entry > procedural skill prose when the skill ships testable behavior. Two sources of truth (skill text + test inline) drift; one source (`scripts/scan.ts` cited by SKILL.md, invoked by test) doesn't. The `security-advisory/SKILL.md` orphan Python reference is now visibly anti-pattern next to this slice.
- Multi-doc mechanical edits (e.g. tools-frontmatter normalize) absolutely warrant fan-out — 32 cavecrew-builder dispatches in single parallel message landed in under a minute wall-clock with sub-process token budgets.
- TS reviewer found a banned `process.exit()` that the builder happily shipped — repo-wide bans need to enter the builder's anchor prompt, not only the reviewer's checklist.

## Decisions

### DEC-024: Plugin observability ceiling

**Rationale**: hero-crew is a Claude Code plugin (no runtime, no log pipeline). When an AC references "observability of X", default to a single grep-able stderr line — not JSON, ULIDs, ISO timestamps, or `.claude/logs/events.jsonl` wiring. Heavyweight observability is the deliverable of FEAT-141 SLICE-B, not a tax every other slice pays.

**Consequences**:
- positive: AC stay testable with a one-line regex; spec-writer can't overshoot via grade-dim transfer.
- positive: removes implicit pressure to build event-stream infra in unrelated slices.
- negative: cross-slice observability correlation impossible until FEAT-141 lands — accepted, since per-slice grading reads grades not logs.

### DEC-025: Executable canonical entry for domain skills

**Rationale**: When a domain skill ships testable scan/audit/check behavior, the skill MUST cite an executable script as the canonical entry (`scripts/<name>.ts`) and the integration test MUST invoke that script directly. Procedural skills (Markdown-only prose describing commands a human or test inlines) duplicate logic between skill body and test, drifting over time. The `security-advisory/SKILL.md` Python orphan reference is the cautionary tale.

**Consequences**:
- positive: one source of truth for skill behavior; test asserts the actual entry point.
- positive: typescript-reviewer gets a real review target with proper type safety + exit code semantics.
- negative: +~80 lines per new skill that ships a script; +1 file in the directory layout.
- negative: skills that are purely procedural advisory (e.g. checklist of what to verify by hand) do NOT need a script — judgment call lives with the skill author.

## What went well

Spec was concrete enough that the builder shipped all 5 Deliverables on the first dispatch with all 8 AC passing in self-verify. Reviewer fan-out caught real issues both reviewers were uniquely positioned to find: inspector noticed the JSON-shape contradiction between SKILL.md (plain text) and inspector.md (JSON object) prose; TS-reviewer caught the `process.exit()` ban, the unsafe `as` cast on caught error, and the `node:test` vs `bun:test` discipline drift. Fix bundle landed all 8 findings in one builder dispatch and verifier re-ran behavior independently.

## What went wrong

Spec-writer's first observability AC overshot the plugin's actual surface — JSON schema + ULID + ISO timestamps for a CLI that emits to stderr. User caught it mid-loop ("this is plugin observability cannot be high") and the slice was trimmed before dispatch. Catching this earlier requires the project-memory rule live in spec-writer's anchor context, not in a parallel memory the spec-writer doesn't read.

Builder's first pass shipped `process.exit()` directly despite CLAUDE.md's repo-wide ban — the rule was in the constitution but not in the builder's per-dispatch anchor prompt. Reviewer caught it; cost was one extra fix cycle.

## What I would do differently next time

Inline the project's observability ceiling rule and the `process.exit()` ban into the spec-writer + builder dispatch prompts directly, not via memory references the subagents don't read. Memory survives across the orchestrator's sessions; subagents start cold and lose the constraint.

For mixed-developer-type slices (skill+script+routing = agent; agent prompt edit = human), surface the human-gate point as an explicit Q before merge, not after — the inspector review caught it cleanly here, but the structure should make the gate inescapable.
