## Decisions

### DEC-TBD-1: Cost-report → span backfill is the canonical substrate for FEAT-165 SLICE-B + FEAT-167 SLICE-C

**Rationale**: The deterministic SHA-256-seeded span schema landed in SLICE-77 becomes the contract for both FEAT-165 SLICE-B (live hook bridge + OTLP exporter) and FEAT-167 SLICE-C (prompt_id + version attr injection). Reusing the same `SpanRecordSchema` across all three slices means: (a) the same Langfuse dataset shape works for backfill + live + eval, (b) `passthrough` on the schema can absorb SDK-side fields without breaking backfill validators.

**Consequences**:
- positive: zero schema drift between FEAT-165 backfill, live OTel hook spans, FEAT-167 prompt-versioned eval spans, and Langfuse dataset items.
- positive: idempotency contract (byte-identical re-run) holds across slice boundaries.
- negative: any schema breaking change cascades across 3 FEATs — `version` field on the schema deferred.

## What went wrong

Initial builder hit AC-1 line caps for both `cost-report-loader.ts` (166/150) and `cost-report-to-spans.ts` (187/130). The slice spec declared the caps in the AC section but the builder didn't budget per-file — collapsed inlines AFTER the review surface. Cheaper to budget per file at planning time.

## What I would do differently next time

Spec writer should emit per-file line budgets as a structured frontmatter field, not free text. Builder reads frontmatter, sets internal cap target per file, refuses to land if any file exceeds. Caps as test-of-record rather than narrative aspiration.
