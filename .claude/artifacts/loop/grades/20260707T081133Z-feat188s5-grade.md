## Decisions

### DEC-TBD: Drift-check stays diagnostic-only, not authoritative

**Rationale**: drift-check.ts's presence check uses recall()'s semantic match rather than an exact id lookup, so a false negative (entry present in astramem but not surfaced by recall()) is possible. Making it authoritative (auto-backfill without human review) risked writing duplicate or spurious entries into the JSONL store off an approximate match.

**Consequences**:
- positive: no risk of corrupting the JSONL derived-duplicate with false-positive backfills
- negative: an operator still has to run drift-check deliberately and interpret its output; it does not (yet) run as a scheduled/CI job

## What went wrong

The memory-delta.ts live-judge AC could not be closed in-session because it depends on an operator-supplied credential not available to the builder/reviewer — this is the third slice in a row (after SLICE-107/FEAT-184 AC-3) to hit the same "AC needs a human with a live credential" pattern, suggesting the credential-gating decision point should be surfaced earlier (at slice-planning time) rather than discovered at review time each time. Separately, this slice-close ceremony discovered that no prior FEAT-188 slice had a slice-linker registry record, grade, or CLI-generated synthesis — the close ceremony for S1a/S1b/S2/S3a/S4/S6 was effectively skipped, which this S5 close could not retroactively fix within scope.

## What I would do differently next time

Also: run the slice-close ceremony (`/loop:slice start` -> `/loop:slice complete` -> `/loop:slice grade`) for every slice as it lands, not retroactively at the end of a multi-slice FEAT — retrofitting one slice file post-hoc (this one) is workable but does not recover the missing registry history for the five slices that shipped before it.
