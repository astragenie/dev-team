## Decisions

### DEC-027: Default mode for executable analyzer skills = PR-review (--changed-only)

**Rationale**: When a domain/workflow skill ships an executable analyzer (regex scan, AST check, security sweep, test-quality lens), the DEFAULT invocation mode must be PR-review (--changed-only --diff-base ref), not bulk audit. PR-review mode is the consumer most-frequent use case — a reviewer running the lens on a slice diff. Bulk audit is opt-in via a --bulk flag for explicit full-tree sweeps. Default-bulk produces noise that reviewers learn to ignore; default-PR-review produces precise signal at the cost the consumer expects. Applies to: security-sweep, test-quality, any future regex-based analyzer skill.

**Consequences**:
- positive: lens output stays signal-rich on the most-common invocation path.
- positive: bulk-audit noise is bounded to intentional sweeps where the consumer chose the wider scope.
- positive: integration tests against fixtures need to pass --bulk explicitly — a tiny extra arg in exchange for honest default semantics.
- negative: consumers who invoke the analyzer for the first time without reading the README get 0 findings on a clean diff. Acceptable: SKILL.md explicitly documents the default; the --bulk flag is named for discoverability.
- negative: requires a --bulk flag to be added to security-sweep too (currently it defaults to bulk-scan-only). Follow-up: SLICE-69 security-sweep should follow this same pattern in a v2.

## What I would do differently next time

Bake the default-mode-safety rule into builder anchor prompts directly. The instinct to default-bulk because that what the integration test needs is a real anti-pattern: it shifts the noise burden onto every future consumer. Add a builder rule: when shipping an executable analyzer, the default mode must be the safest mode for the most-common consumer. Test-convenient flags are opt-in via explicit args.

Move the calibrate-before-AC-pass requirement into the spec-writer template for any slice that ships a regex-based heuristic. The AC-6 gate caught this slice; the alternative was a v1 release with 99% false-positive rate. Make the pattern explicit so future spec-writers reach for it without a triage_notes nudge.

Investigate the builder cutoff pattern as a real operational issue. Three slices in one session with the same failure mode is signal. Either the builder budget is too tight, the prompt is too long, or the handoff write step is unreliable. File a FEAT.
