## Lessons

- **Verify the FEAT before implementing it.** Half of FEAT-138 (the real drift on `valid-feat-contracts.ts`, AC#1) was already fixed by an interim commit (`2f8fbb6`). Reproducing locally first turned a "fix two failures" task into a "fix one narrow conflation + lock it" task — no redundant regen.
- **Negative fixtures need their own behavior lock.** The existing negative-fixture test used `checkDrift:false`, but CI runs it with `checkDrift:true`. The untested gap was exactly where the bug lived. A negative fixture that "fails as expected" can still fail for the *wrong reason*.
- **Shell/tool mismatch bites quietly.** Two self-inflicted errors this session from the same root: `git log --grep -E` (grep-flag syntax on git) and a PowerShell `@'…'@` here-string passed through the Bash tool. Both produced confusing, non-obvious failures. When a command errors oddly, suspect the shell dialect first.

## Decisions

### DEC-013: Gate contract drift-check on `errors.length === 0`

**Rationale**: Comparing committed TS against regenerated TS is only meaningful for an otherwise-valid spec. When redocly lint fails (or the spec is not OpenAPI 3.1, or TS generation throws), the regenerated output is garbage and the drift comparison is noise. Gating the drift block on `errors.length === 0` makes drift a *second-stage* check that only runs once the spec is structurally sound.

**Consequences**:
- Negative fixtures fail for their intended reason (lint) only — no conflated `drift: committed TS missing`.
- Valid specs are unaffected: real drift is still caught (verified — the existing drift test uses `runLint:false` with a drifted TS, so `errors` is empty at the gate and drift runs).
- Minor: a spec that lints clean but fails the 3.1-marker check will now also skip drift. Acceptable — an invalid spec shouldn't be drift-compared anyway.
