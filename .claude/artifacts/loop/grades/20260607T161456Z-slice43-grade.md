## Lessons

- Windows libuv crash `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` in `win/async.c` triggers when `process.exit(0)` is called inside async `main()` in scripts with 3+ deep TypeScript imports under `--experimental-strip-types`. The crash is deterministic on Node v24.16.0 / Windows 11.
- Fix: replace early `process.exit(0)` with `process.stdin.resume(); return` in the gate-off path. For other early-exit paths after `readStdin()`, plain `return` suffices. Removing `process.exit(0)` from the catch handler also helps.
- The crash does NOT occur in simpler hooks (fewer imports) or when `process.exit(0)` is called at top level (not inside async context). The race condition is specific to async main + deep import chain.
- `format:check` must be run after migrating files since Prettier formats `.ts` differently in some edge cases (template literals, trailing commas).

## Decisions

### DEC-011: Use stdin.resume() + return instead of process.exit(0) in async hooks

**Rationale**: `process.exit(0)` inside async main() with deep import chains crashes libuv on Windows (Node v24 + --experimental-strip-types). Using `process.stdin.resume()` then `return` allows natural process exit, avoiding the race condition.

**Consequences**:
- All 5 cost-hygiene hook tests now pass on Windows
- Slightly longer exit time in gate-off path (waits for stdin EOF), but negligible in practice

## Surprises

- The crash only manifests with 3+ TypeScript imports and async context — simpler hooks were unaffected
- Minimal reproductions did NOT reproduce the crash (PowerShell heredoc was stripping template literals), making diagnosis harder

## Followups

- SLICE-44/45: tests/*.mjs → .ts migration (Phase 4)
- Consider applying same `stdin.resume()` pattern to other hooks proactively if they ever get deeper import chains

## What went well

- Systematic isolation: running each hook directly verified the crash was specific to check-redundant-read.ts
- The fix was minimal and targeted — 3 lines changed

## What went wrong

- PowerShell string interpolation in heredocs ate TypeScript template literals (`${code}` was interpolated), causing false "can't reproduce" from minimal test scripts

## What I would do differently next time

- Write test files to disk first, then run them — avoid PowerShell heredoc for TypeScript that uses `${}` template literals
