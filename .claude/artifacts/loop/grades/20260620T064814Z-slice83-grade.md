## Lessons

- Hook static-import graph is the right level to gate on for plugin-cache safety. Gating only at the bridge's top-level dep imports would have missed the v0.37.1 bug because the bridge wasn't statically reachable after the lazy-import fix — the hook was. Future telemetry-adjacent regression gates should target hook entries, not library internals.
- The "copy source + mirror node_modules minus dep X" pattern is a clean way to simulate partial-install plugin-cache shapes. Symlink type='junction' on Windows gives admin-free dir symlinks; the same code works on POSIX with type='dir'. Reusable for future plugin-cache regression gates.
- Sanity-checking a regression gate by re-introducing the original bug shape (then reverting) is cheap and catches a whole class of "test that passes for the wrong reason" bugs. Took ~2min, caught that my first sim (top-level import in otel-bridge.ts) didn't trigger because the hook gate shielded it. Moved the sim to the hook layer, saw the expected failure, reverted, confirmed baseline green.

## Surprises

- First regression sim didn't fail. Lazy-import in the hook (the other half of the v0.37.2 fix) means a re-introduced top-level `@opentelemetry/api` import in `otel-bridge.ts` is no longer statically reachable from the hook startup. The bug class is narrower than originally framed: it's specifically about the hook's static import graph, not the bridge's. The gate as written is correct (it spawns the hook, not the bridge), but the framing in FEAT-168 body conflates the two layers.

## Followups

- Consider extending the gate to assert disabled-path stderr is COMPLETELY empty (today it tolerates anything that isn't `@opentelemetry` / `ENOENT` / `MODULE_NOT_FOUND`). Would catch other hook-graph regressions (e.g., a stray `console.error` in `loadTelemetryConfig`'s YAML-parse error branch). Out of scope for FEAT-168.
- The `cp` + symlink fan-out runs in series and copies ~700 entries from `node_modules`. Test wall-clock is ~1.6s for 3 cases on Windows. If the suite grows to N hooks, parallelize the temp-dir setup via `Promise.all`. Out of scope today.

## What went well

Direct-build path (skip slice ceremony at the start, do ceremony at close) fit the micro-build well: ~30min wall clock from FEAT-filing through merge. Sanity-check loop (write test → simulate bug → see failure → revert → confirm baseline) added confidence the gate actually works, not just passes. Doc note co-located with the constraint (`docs/observability/langfuse-bridge.md` rather than `docs/standards/`) means the next contributor touching telemetry sees the rule.

## What went wrong

FEAT-168 body framed the bug class as "any top-level @opentelemetry/* import in the hook graph" but the AC and initial test mental model treated the bridge as the canonical place to gate. Discovery during sim. Cost: ~5 minutes to realize + relocate the sim. Documenting the framing in the FEAT body up front would have saved the round-trip.

## What I would do differently next time

When writing a regression gate FEAT for a hotfix, articulate in the FEAT body which layer the static-import graph terminates at, not just the symptom. The mental model "static import graph reachable from hook process entry" is more precise than "any top-level @opentelemetry/* import" because the latter false-positives on bridge-internal imports that aren't reachable from a sound hook gate.
