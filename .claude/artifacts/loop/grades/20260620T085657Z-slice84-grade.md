## Lessons

- **Hybrid orchestration kept ceremony cost down.** Builder dispatched once via Agent tool, returned mid-thought with TS errors (stale IDE diagnostic — actual `tsc --noEmit` was clean per memory feedback_stale_ide_diagnostic.md). Main thread picked up + finished inline (test budget trim + verify gates) per feedback_finish_stuck_agent_inline.md. Saved ~$3 vs re-dispatching the builder for a 30-line trim.
- **Line budgets in slice frontmatter caught the test-file overage at the right time.** Spec declared `tests/agent-stats-aggregator.test.ts: 300`. Builder shipped 333. Trim was deterministic (compress fixtures via `mk` helper + strip section dividers) and the budget check was a single `wc -l` away from `commit`. Validates the feedback_line_budgets_in_spec_frontmatter.md pattern.
- **Two-reviewer parallel fan-out (inspector + typescript-reviewer) found complementary issues.** Inspector caught the regex-misses-rejected advisory (semantic). TypeScript reviewer caught the unguarded GradeRecord cast + 2 LOW cast-style nits (type-system). Single reviewer would have missed one axis. Validates the SLICE-82 reviewer-ladder shape for typed/observable slices.
- **Applying MEDIUM review findings in-slice (before validation) costs less than deferring.** The cast guard + JSONL comment + type-predicate filter were a 3-edit, ~5-minute fix. Deferring to a follow-up slice would have meant another full review cycle on the same file. The MEDIUM-2 (tsconfig verbatimModuleSyntax) was correctly deferred because it's repo-wide, not slice-scope.

## Surprises

- Runner `slice complete` auto-moved FEAT-159 → done/ even though the slice spec explicitly said "FEAT stays in in-progress until follow-up slices close". Had to manually move back + add `partial_progress` frontmatter. Suggests the runner CLI lacks a `--feature-stays-in-progress` flag, or the convention is "every slice close → FEAT done" by default. Worth a followup in the runner repo: surface a `partial_progress` field schema and respect it during slice-complete.

## What went well

- Slice spec was specific enough that the builder didn't have to invent. 7 ACs + 4 file budgets + explicit out-of-scope list + named reviewers.
- Reviewers ran in parallel via background dispatch — saved wall clock without main thread context bloat.
- AC-3 + AC-6 live smokes ran in ~10 seconds. The aggregator's empty-source fail-safe was the right design call.

## What went wrong

- Builder cut off mid-thought during the test-file refactoring pass (complexity warning recovery). Stale IDE diagnostic appeared in main thread post-cutoff (per the memory pattern, the actual repo state was already clean). Cost a verify-via-typecheck round-trip that wouldn't have happened if the builder had completed its own self-verify gates before returning.
- Runner CLI auto-promoting FEAT to done/ on slice complete is a surprise (above). Cost ~2 minutes of remediation. Document or fix upstream.

## What I would do differently next time

When a slice is explicitly Part-A of a multi-deliverable FEAT, set `multi_slice_parent: true` (or similar) in the slice frontmatter and check whether the runner CLI respects that flag before completion. If not, do the FEAT-stays-in-progress remediation as part of the slice-complete sequence rather than as a manual after-step.
