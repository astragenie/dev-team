# Migrations

Schema migration frameworks, zero-downtime techniques, rollback scripts, and monolith decomposition.

## Migration principles

- Every schema change is a versioned, reviewed migration file — no ad-hoc console changes in production.
- Every migration has a corresponding rollback (down) script.
- Migrations are idempotent where possible (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`).
- Large data backfills run in batches, not a single statement, to avoid lock escalation and timeout.
- Test migrations against a copy of production data volume before live cutover.

## Migration script structure

```python
# Example: migration framework with automatic rollback on failure

async def execute_migration(db, migration_script):
    migration_id = generate_id()
    checkpoint = await create_checkpoint(db)
    try:
        async with db.transaction():
            for step in migration_script["steps"]:
                await db.execute(step["sql"])
                await db.execute(
                    "INSERT INTO migration_history (migration_id, step, sql, executed_at) "
                    "VALUES ($1, $2, $3, now())",
                    migration_id, step["step_number"], step["sql"]
                )
            await db.execute(
                "INSERT INTO migrations (id, name, version, executed_at, status) "
                "VALUES ($1, $2, $3, now(), 'completed')",
                migration_id, migration_script["name"], migration_script["version"]
            )
    except Exception as e:
        await rollback_to_checkpoint(db, checkpoint)
        raise MigrationError(f"Migration failed at step, rolled back: {e}")
```

## Zero-downtime migration patterns

### Expand-Contract (Blue-Green schema)

Safest approach for column renames or type changes — avoids locking rows:

1. **Expand** — add the new column alongside the old one; backfill in batches.
2. **Dual-write** — application writes to both columns simultaneously.
3. **Migrate reads** — switch application reads to the new column; verify in prod.
4. **Contract** — once the old column is no longer read, drop it in a follow-up migration.

### Adding a column

```sql
-- Safe: ADD COLUMN with DEFAULT does not rewrite the table in Postgres 11+
ALTER TABLE orders ADD COLUMN archived_at TIMESTAMP WITH TIME ZONE DEFAULT NULL;
```

### Adding a NOT NULL column

```sql
-- Unsafe (locks): ALTER TABLE ... ADD COLUMN col TEXT NOT NULL DEFAULT ''
-- Safe pattern:
ALTER TABLE orders ADD COLUMN notes TEXT;                 -- step 1: add nullable
UPDATE orders SET notes = '' WHERE notes IS NULL;         -- step 2: backfill in batches
ALTER TABLE orders ALTER COLUMN notes SET NOT NULL;       -- step 3: add constraint
ALTER TABLE orders ALTER COLUMN notes SET DEFAULT '';     -- step 4: set default
```

### Renaming a column

Follow Expand-Contract above. Never rename a column directly in a live schema — it breaks running application instances.

## Monolith-to-microservices decomposition

Decomposing a monolithic database into per-service databases without downtime:

1. **Identify bounded contexts** — map tables to owning service; flag shared tables.
2. **Strangler-fig sequence** — extract one context at a time; dual-write to old and new store during transition.
3. **Dual-write migration**:
   - Service writes to both old monolith table and new service DB.
   - Read from new DB; fall back to old on miss.
   - Once confidence is high, stop writing to old table; eventually drop it.
4. **Data-consistency checkpoints** — run hash reconciliation queries to verify row counts and checksums match across stores.
5. **Cutover runbook** — includes pre-cutover snapshot, traffic switch step, verification step, and rollback trigger conditions.

## ORM migration frameworks

- **Prisma** — `prisma migrate dev` (development), `prisma migrate deploy` (CI/prod). Never skip `prisma migrate status` before deploy.
- **SQLAlchemy / Alembic** — `alembic upgrade head`; always review autogenerated migrations before applying.
- **ActiveRecord** — `rails db:migrate`; use `strong_migrations` gem to detect dangerous operations.
- **TypeORM** — `typeorm migration:run`; prefer explicit migration files over `synchronize: true` in production.

## Anti-patterns

- Running `synchronize: true` (TypeORM) or `createSchemaIfNotExists` in production — risk of accidental DROP.
- Long-running `ALTER TABLE` on large tables without `CONCURRENTLY` where available.
- Deploying new application code before the migration it depends on has run.
- Skipping the rollback script — "we'll never need it" is how you end up needing it at 2 AM.
- Backfilling millions of rows in a single UPDATE without batching — causes table locks and replication lag.
